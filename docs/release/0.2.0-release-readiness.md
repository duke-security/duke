# 0.2.0 Release-Readiness Checklist

This document records Duke's current release-readiness state and separates
the distinct release mechanisms so each can be planned and gated
independently. **Nothing here is an instruction to release.** This slice
performs none of the release actions below.

## Current facts

- **Source version is now `0.2.0`** on the `release/0.2.0` branch (single
  source in `pyproject.toml`, surfaced to `duke version` via
  `importlib.metadata`). `main` remains at `0.1.0` until the release merges.
- **No Git tags currently exist** (`git tag -l` is empty).
- **A Git remote is configured**: `origin` =
  `https://github.com/umargambari/duke-security.git` (verified; the
  repository is intentionally empty, so `git ls-remote` returns zero refs).
- **Licensing is resolved**: Duke is licensed under the Apache License 2.0
  (root `LICENSE` file, `license = "Apache-2.0"` + `license-files`
  metadata, README License section updated).
- **Project URLs are set** under `[project.urls]` in `pyproject.toml`
  (Homepage / Repository / Documentation / Issues), pointing at the
  `umargambari/duke-security` repository.
- **Build frontend is available**: `build` is declared in the `dev` extra;
  both **wheel and sdist** build and were inspected.
- **Scenario-version policy is resolved**: each scenario's metadata/content
  version is independent of the Duke package version (see
  `docs/scenarios/scenario-authoring.md`); neither scenario changes here.
- **`0.2.0` is not publicly released yet** — the release commit, merge,
  local tag, push, and GitHub release all remain **pending** on this
  branch.
- **T1566 is outside the `0.2.0` scope.** T1566.002 is proposed future work
  (see ROADMAP), not implemented or registered.
- **`0.2.0` scope is the completed T1078 + T1110 portfolio plus the Phase 1
  portfolio and release-metadata documentation** (component and lifecycle
  diagrams, README showcase, reproducible demonstration, and this readiness
  checklist).

The two complete production scenarios (T1078 Valid Accounts and T1110
Brute Force / Password Spraying) each provide all **seven** lifecycle
capabilities: simulation, detection, investigation, response, validation,
reporting, and learning.

## Distinct release mechanisms

### 1. Documentation readiness

The portfolio must be complete and current before any version, tag, or
release step:

- [ ] `docs/architecture/components.md` — component diagram accurate
- [ ] `docs/architecture/lifecycle.md` — lifecycle + data-flow accurate
- [ ] README showcase concise and accurate
- [ ] `docs/development/reproducible-demo.md` reproducible from a fresh clone
- [ ] This checklist reviewed and correct

### 2. Source version bump

Advancing the packaging version from `0.1.0` to `0.2.0`.

Prerequisites:

- [ ] Phase 1 documentation complete and reviewed on `main`
- [x] License and metadata resolved: **Apache License 2.0** (root `LICENSE`
      file, `license = "Apache-2.0"` + `license-files`, README License
      section updated) — done in the release-metadata-hardening slice
- [ ] Full quality gates passing (pytest, ruff, mypy)
- [ ] CHANGELOG contains a drafted `0.2.0` release section

Outcome: `pyproject.toml` version changes to `0.2.0`; `duke version`
reports `0.2.0` once the package is rebuilt/installed. This is a **code
change** and is intentionally **not** performed by the hardening slice.

### 3. Package / build verification

Confirm the package installs and runs from a fresh build, not just from the
source tree:

- [ ] Verified installation instructions (`docs/development/environment-setup.md`)
- [x] Fresh-environment install test (`pip install` of a built wheel in a
      clean venv) — done in the hardening slice
- [x] CLI smoke tests in the installed environment (`version`, `scenarios`,
      and `simulate T1078` / `simulate T1110`) — done in the hardening slice
- [x] Build verification: **both wheel and sdist** built with `python -m
      build` and contents inspected — done in the hardening slice
      (`build` is now declared in the `dev` extra)
- [x] Secret / local-configuration scan (ensure no credentials, keys, or
      local paths ship in the package) — done in the hardening slice; the
      archives carry no tests, secrets, caches, or local configuration

### 4. Annotated Git tag

An immutable release marker once the version bump is committed on `main`.

Prerequisites:

- [ ] Source version bump committed
- [ ] Clean, reviewed `main`
- [ ] Conformance suite passing at the tagged commit
- [ ] Tag command reviewed (e.g. `git tag -a v0.2.0 -m "0.2.0"`)

### 5. Remote / push requirements

Publishing a tag or a GitHub release requires a remote, which **does not
exist today**.

Prerequisites:

- [ ] A Git remote configured (none is configured as of this checklist)
- [ ] Push rights to the target repository
- [ ] `v0.2.0` tag pushed

### 6. GitHub release

Public distribution or announcement.

Prerequisites:

- [ ] Remote configured and tag pushed (above)
- [ ] Release notes drafted from the CHANGELOG
- [ ] Target repository exists and the release is authorized

## Recommendation (not executed here)

For `0.2.0` — Duke's first public-ready cut — ship **all three** of source
version bump, annotated tag, and GitHub release, against the now-configured
`origin` remote. This branch performs the version bump (to `0.2.0`) and the
CHANGELOG finalization, but it does **not** create a tag, push, or create a
GitHub release; those remain separate, explicitly authorized steps.
